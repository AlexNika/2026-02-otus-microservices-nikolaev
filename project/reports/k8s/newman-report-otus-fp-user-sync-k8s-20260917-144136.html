Collection Description
E2E сценарий асинхронной репликации контактных данных пользователя (USER -> NOTIFICATION, DELIVERY): 1. Регистрация пользователя с phone и 2 адресами доставки -> 201. В одной транзакции в общий outbox записываются UserCreatedEvent (USER -> BILLING) и UserSyncEvent (полный снимок контактов и адресов). 2. Логин -> JWT. 3. GET /api/v1/profile - телефон и адреса с созданными id. 4. PUT /api/v1/profile (Bearer) - смена phone, обновление адреса #1 (isDefault=false), удаление адреса #2, добавление нового адреса без id. Публикуется новый UserSyncEvent. 5. Проверки read-моделей через внутренние эндпоинты (заголовок X-Internal-API-Key): GET {{baseUrl}}/internal/contacts/user/{{userId}} и GET {{baseUrl}}/internal/delivery/user-addresses/{{userId}}. 6. Повторный PUT с тем же телом (имитация повторной доставки на уровне API) -> read-модели без изменений и без дублей (идемпотентность: NOTIFICATION - processed_messages + PK user_id, DELIVERY - upsert по (user_id, source_address_id) + delete-not-in). Запуск: из fp/ выполнить scripts/06-run-postman-k8s.ps1 (newman) — ключ X-Internal-API-Key читается из fp/.env (или задаётся параметром -InternalApiKey) и передаётся newman через --env-var internalApiKey. Вручную: newman run postman/k8s/otus-fp-user-sync-k8s.postman_collection.json -e postman/k8s/k8s.postman_environment.json --env-var internalApiKey=<ключ из fp/.env>. Предпосылки: запущен minikube и установлен релиз fpchart (scripts/03-helm-fp-install.ps1); домен arch.finalproject резолвится на IP ingress-контроллера (minikube tunnel и/или запись в файле hosts). Локальный туннель на 127.0.0.1 не требуется. Ручные SQL-проверки (kubectl port-forward на pod соответствующего PostgreSQL): -- 1) Outbox: события USER_SYNC публикуются (event_type='USER_SYNC') SELECT id, event_id, event_type, status, attempts, created_at, sent_at FROM user_outbox WHERE event_type = 'USER_SYNC' ORDER BY id; -- 2) NOTIFICATION read-модель: ровно одна строка на пользователя SELECT user_id, email, phone, updated_at FROM notification_contacts WHERE user_id = <userId>; -- 3) DELIVERY read-модель: адреса без дублей (UNIQUE(user_id, source_address_id)) SELECT user_id, source_address_id, full_address, city, postal_code, is_default, updated_at FROM delivery_user_addresses WHERE user_id = <userId> ORDER BY source_address_id;
